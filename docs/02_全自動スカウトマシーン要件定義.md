# 全自動スカウトマシーン 要件定義（ドラフト）

作成日: 2026-07-27 / 状態: **確認事項の回答待ち（実装未着手）**

---

## 1. 目的

候補者を1人ずつ手作業で処理している現在のフローを、**1回の操作で最大20件を連続自動処理**する形にする。
「ひと段落」= 20件の処理完了（送信＋NGスキップの合計。※Q1で確認）。

## 2. 現在のフローと自動化後のフロー

```
【現在】人が毎回:
 プロフィールを開く → スカウト画面を開く → 青ボタン → (自動生成・入力) → 人が送信

【自動化後】人は開始ボタンを押すだけ:
 ┌─ 候補者ごとに繰り返し(最大20件) ─────────────┐
 │ ① プロフィール画面を開いて情報取得              │
 │ ② NG判定(下記) → NGならスキップして次へ         │
 │ ③ スカウト画面を開く                            │
 │ ④ Geminiで生成 → フォーム入力                   │
 │ ⑤ 検証(破損・混入・文字数) → NGならスキップ      │
 │ ⑥ 送信(※方式はQ2)                              │
 │ ⑦ 結果を記録、待機時間を置いて次へ              │
 └──────────────────────────────┘
 → 完了レポート表示(送信◯件/スキップ◯件と理由)
```

## 3. NG判定（自動スキップ条件）

プロフィールのテキストから**拡張機能がルールベースで判定**する（Geminiに判定させない。決定的・確実にするため）。

| # | 条件 | 判定方法 |
|---|---|---|
| NG1 | 職種がパティシエ | 職種・職務経歴に「パティシエ」を含む |
| NG2 | 寿司職人 | 職種・職務経歴に「寿司職人」（表記ゆれ: 鮨・すし職人）を含む |
| NG3 | 転職回数 ≥ 年齢の10の位 | 例: 35歳(10の位=3)で転職3回以上→NG。28歳(2)で2回以上→NG |

**NG3の未確定点（Q3）:**
- グルメキャリーの表記は「◯社経験」。**転職回数 = 社数 − 1** とみなすか、**社数そのもの**を使うか
- 年齢または社数が読み取れない場合の扱い（安全側=スキップ を推奨）

判定の対象範囲（職種欄のみか、職務経歴全体か）もQ3で確認。
例: 過去にパティシエ経験があるが現職はホール、はNGか？

## 4. 送信方式 — 最重要の設計判断（Q2）

これまでの鉄則「**最後の送信ボタンは必ず人間が押す**」（誤送信防止）を変更することになる。選択肢:

| 案 | 内容 | リスク | 人の作業 |
|---|---|---|---|
| A: 完全自動 | 送信まで機械が押す | 誤送信を人間レビューなしで負う | 開始ボタンのみ |
| B: 半自動（準備マシーン） | 20件を「入力済み・検証済み」まで自動で準備し、送信は人が1件ずつ確認して押す | 誤送信リスクは現状同等 | 20回の確認+送信クリック |
| C: 段階運用 | まずBで数バッチ回し、品質に問題なければAへ切替（設定フラグ1つ） | 段階的に低減 | 最初だけB |

**推奨: C**。品質は15〜25%評価まで来ているが、「有気休暇」のような確定文破損が現実に起きており、検証をすり抜ける新種の事故がゼロとは言い切れないため。

**技術的な未確定点**: スカウト画面の「送信」ボタン（`#btn_conf`）を押した後の挙動が未検証。確認画面が挟まるなら、そのページのHTML（またはスクリーンショット）が必要。

## 5. 対象候補者リストの供給方法（Q1）

20件を「どこから」取るか。

| 案 | 内容 | 向き不向き |
|---|---|---|
| a: 検索結果から自動 | 会員検索で条件を絞った一覧ページから、上から順に未送信の候補を自動で拾う | 最も全自動。一覧ページのHTML提供が必要 |
| b: 人が選んでキューに積む | プロフィールを開くたび「キューに追加」しておき、あとで一括実行 | 候補者の目利きは人間が担保 |
| c: 開いた履歴から | すでに実装済みのプロフィール自動保存を流用し、保存済み＆未送信の候補を処理 | 追加UIが最小 |

## 6. スカウト画面の必須項目の自動化（Q4）

- **求人票**（必須・選択）: どの求人票を使うか。毎回同じものを自動選択する場合、その名称の指定が必要
- **定型文**: 使わない想定でよいか（生成文で全文を賄う）

## 7. 安全設計（実装必須としたい項目）

1. **ドライランモード**: 送信ボタンを押さない以外すべて実行し、20件分の生成結果をレポートで確認できる。初回バッチは必ずドライラン
2. **検証ゲート**: 既存の4段検証（件名/本文長・プレースホルダー残り・英単語混入・確定文破損20フレーズ）のいずれかに引っかかったら、**自動送信せず**スキップして記録
3. **二重送信防止**: 送信済み会員IDを記録し、同じ候補者には二度と送らない（過去の手動送信分は記録がないため対象外。※スカウト履歴欄から判定できるならそれも併用）
4. **上限**: 1バッチ最大20件、1日の送信上限も20件（既存バッジカウンタと連動）
5. **ペース制御**: 1件ごとに30〜90秒のランダム待機（サイトへの負荷と機械的アクセスの緩和。20件で約30〜60分）
6. **緊急停止**: パネルに停止ボタン。処理中の1件を終えた時点で停止
7. **完了レポート**: 会員ID・結果（送信/スキップ）・スキップ理由の一覧を表示し、コピーできる形にする

## 8. リスク（正直な申告）

- **誤送信**: 完全自動では、検証をすり抜けた不備メールが人間レビューなしで送られる。検証は「既知の事故パターン」しか防げない
- **アカウントリスク**: 短時間の機械的な連続送信は、サイト運営側から見て通常と異なる利用パターンになる。ペース制御で緩和するが、ゼロにはならない
- **画面遷移の未知**: 送信後の遷移が未検証のため、実装後に 1件→3件→20件 の段階テストが必須

## 9. 実装しない（スコープ外）

- 候補者の検索条件の自動設定（検索は人間が行う前提）
- 返信への自動対応
- 20件を超える連続処理
