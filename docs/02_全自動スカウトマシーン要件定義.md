# 全自動スカウトマシーン 要件定義（確定版）

作成日: 2026-07-27 / 状態: **要件確定。実装前に「§11 実装前に必要な情報」の提供待ち**

## 0. 確定した決定事項（依頼者回答）

| 項目 | 決定 |
|---|---|
| 送信方式 | **A: 完全自動**（送信まで機械が押す）。ただし「Geminiの出力の不備に気づけないこと」が絶対NG → 検証機構を最重要要件とする（§7） |
| 候補者の供給 | **検索結果一覧から自動**（会員検索で絞った一覧の上から順に、未送信の候補を拾う） |
| 転職回数の定義 | **経験社数 − 1**。年齢・社数が読み取れない場合は安全側でスキップ |
| NG職種の判定範囲 | **過去の職務経歴に1つでもあればNG** |
| 求人票 | **選択済みの状態を使う**（拡張は自動選択しない） |

---

## 1. 目的

候補者を1人ずつ手作業で処理している現在のフローを、**1回の操作で最大20件を連続自動処理**する形にする。
「ひと段落」= 20件の処理完了（送信＋NGスキップの合計）。

**重要: 一斉送信ではない。** 処理は完全な直列（1件ずつ）で、1件の送信が終わってから5〜10秒おいて次の1件に進む。
同時に複数件を処理・送信することはない。「20件」は停止ラインであり、まとめ送りの単位ではない。
1件あたり約1〜1.5分（内訳: Gemini生成30〜60秒＋AI二次検査15〜30秒＋画面遷移・入力10秒＋待機5〜10秒）、**20件で約20〜30分**。
所要時間の下限はGemini自体の生成速度で決まる。さらに短縮するには二次検査の省略が必要だが、検証重視の方針と矛盾するため行わない。

## 2. 現在のフローと自動化後のフロー

```
【現在】人が毎回:
 プロフィールを開く → スカウト画面を開く → 青ボタン → (自動生成・入力) → 人が送信

【自動化後】人は開始ボタンを押すだけ:
 ┌─ 候補者ごとに繰り返し(最大20件) ─────────────┐
 │ ① プロフィール画面を開いて情報取得              │
 │ ② NG判定(下記) → NGならスキップして次へ         │
 │ ③ スカウト画面を開く                            │
 │ ④ Geminiで生成 → フォーム入力                   │
 │ ⑤ 検証(破損・混入・文字数) → NGならスキップ      │
 │ ⑥ 送信(※方式はQ2)                              │
 │ ⑦ 結果を記録、待機時間を置いて次へ              │
 └──────────────────────────────┘
 → 完了レポート表示(送信◯件/スキップ◯件と理由)
```

## 3. NG判定（自動スキップ条件）

プロフィールのテキストから**拡張機能がルールベースで判定**する（Geminiに判定させない。決定的・確実にするため）。

**NG職種（職務経歴・職種欄に1つでも含まれればNG。確定）:**

| 職種 | 表記ゆれの例 |
|---|---|
| パティシエ | パティシエール、製菓 |
| 寿司職人 | 鮨職人、すし職人 |
| ソムリエ | — |
| バーテンダー | バーテン |
| パン職人・パン製造 | ブーランジェ、製パン |
| バリスタ | — |

※「料理長・料理長候補」「経営者（自営・オーナー）」は**NGにしない**（依頼者確認済み 2026-07-27）。
マネジメント実績型の優良候補として引き続きスカウト対象。
（委託契約も経営者とセットの項目だったため外している。業務委託だけNGに残したい場合は要指示）

**NG3: 転職回数 ≥ 年齢の10の位（確定）**

- 転職回数 = 経験社数 − 1（グルメキャリーの「◯社経験」表記から算出）
- 例: 35歳（10の位=3）で4社経験（転職3回）→ NG。28歳（2）で3社経験（転職2回）→ NG
- 年齢または社数が読み取れない場合は判定不能として**スキップ**（送信しない）

## 4. 送信方式（確定: A 完全自動）

これまでの鉄則「最後の送信ボタンは必ず人間が押す」を変更し、送信まで自動化する。
依頼者の条件: **「Geminiの出力が中途半端・ミステイクであることに気づけない」ことが絶対NG**。
そのため、§7の多層検証ゲートを送信の前提条件とし、**1つでも不合格なら絶対に送信しない**（再生成→それでもダメならスキップ）。

初回バッチのみドライラン（送信ボタンを押さない）で全件の生成品質を確認してから、本番運用に入る。

**技術的な未確定点**: スカウト画面の「送信」ボタン（`#btn_conf`）を押した後の挙動が未検証。確認画面が挟まるなら、そのページのHTML（またはスクリーンショット）が必要（§11）。

## 5. 対象候補者リストの供給（確定: 検索結果一覧から自動）

- 運用フロー: 人間が会員検索で条件を絞る → 一覧ページで「自動スカウト開始」ボタンを押す → 拡張が一覧の上から順に候補を処理する
- 送信済み・スキップ済みの会員IDは記録し、次回バッチでは飛ばす（一覧に同じ人がいても二重処理しない）
- 20件に満たない場合（一覧の候補が尽きた場合）はそこで終了しレポート表示
- **実装には検索結果一覧ページのHTMLが必要**（§11）

## 6. スカウト画面の必須項目（確定）

- **求人票**: サイト側で選択済みの状態を前提とし、拡張は操作しない
  - 実装時の検証項目: 自動遷移で開いたスカウト画面でも求人票が選択済みになっているか。なっていない場合は「求人票未選択」としてスキップし、レポートに記録する（無選択のまま送信しない）
- **定型文**: 使用しない（生成文で全文を賄う）

## 7. 検証ゲート（最重要要件）— 不合格なら絶対に送信しない

「Geminiの出力の不備に気づけないまま送信される」ことを防ぐため、送信前に3層の検証を全通過することを送信条件とする。

**第1層: ルールベース検証（実装済みの拡充）**
- 件名10〜70文字 / 本文300文字以上（下限を引き上げ）
- プレースホルダー（{{ }}）残りなし
- 日本語文中の英単語混入なし
- 確定文20フレーズの完全一致（「出出店」「有気休暇」型の破損検知）
- 禁止語句（プロンプトの使用禁止語句リスト）が本文に含まれていない ← 新規追加
- NG職種の語が本文に混入していない（パティシエ等をメール本文に書いてしまう事故の防止）← 新規追加

**第2層: AI二次検査（新規）**
- 生成されたメールを、**別の検査プロンプトでGeminiにもう一度読ませ**、次の観点でPASS/FAILを判定させる:
  誤字・脱字 / 文の途切れ・不自然な断片 / 候補者情報と矛盾する記述 / 敬語の破綻 / 意味の通らない文
- FAILの場合は理由つきで返させ、レポートに記録

**第3層: 再生成と最終判断**
- 第1層または第2層で不合格 → 1回だけ自動再生成 → 再検証
- それでも不合格 → **送信せずスキップ**し、生成文と不合格理由をレポートに残す（人が後で手動判断できる）

## 8. 安全設計（実装必須）

1. **ドライランモード**: 送信ボタンを押さない以外すべて実行。初回バッチは必ずドライランで、20件分の生成結果と検証結果をレポートで確認してから本番へ
2. **二重送信防止**: 送信済み会員IDを記録し、同じ候補者には二度と送らない（過去の手動送信分は記録がないため対象外。スカウト履歴欄から判定できるなら併用）
3. **上限**: 1バッチ最大20件、1日の送信上限も20件（既存バッジカウンタと連動）
4. **ペース制御**: 1件ごとに5〜10秒のランダム待機（20件で約20〜30分。生成と二次検査自体が1件1分前後かかるため、送信間隔は実質1分以上空く）
5. **緊急停止**: パネルに停止ボタン。処理中の1件を終えた時点で安全に停止。ブラウザを閉じた場合も再開時に続きから
6. **完了レポート**: 会員ID・結果（送信/スキップ）・スキップ理由（NG職種/転職回数/判定不能/検証不合格/求人票未選択 等）の一覧を表示し、コピーできる形にする

## 9. リスク（正直な申告）

- **誤送信**: 完全自動では、3層検証をすり抜けた不備メールが人間レビューなしで送られる可能性が残る。検証は既知の事故パターンとAI検査で大幅に減らせるが、ゼロは保証できない
- **アカウントリスク**: 短時間の機械的な連続送信は、サイト運営側から見て通常と異なる利用パターンになる。ペース制御で緩和するが、ゼロにはならない
- **画面遷移の未知**: 送信後の遷移が未検証のため、実装後に ドライラン→1件→3件→20件 の段階テストが必須
- **NG判定の表記ゆれ**: NG職種はテキスト一致で判定するため、想定外の表記（例: 英字表記のSommelier等）はすり抜ける可能性がある。運用しながらゆれリストを追加していく

## 10. 実装しない（スコープ外）

- 候補者の検索条件の自動設定（検索は人間が行う前提）
- 返信への自動対応
- 20件を超える連続処理

## 11. 実装前に必要な情報（提供依頼）

1. **検索結果一覧ページのHTML**（会員検索の結果一覧。候補者の並び・会員IDリンク・スカウト画面への導線が分かる部分）
2. **スカウト画面で「送信」を押した後の挙動**（確認画面が出るか、即送信か。出るならそのページのHTMLかスクリーンショット）
3. （可能なら）一覧に「スカウト済み」の印が出るか（二重送信防止の補助に使えるため）

この3点が揃い次第、実装に着手する。実装順: NG判定＋一覧巡回 → 生成・検証ゲート → ドライラン → 送信自動化。
